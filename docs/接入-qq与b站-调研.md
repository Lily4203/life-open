# QQ 与 B 站接入：能做什么、代价是什么、先做哪个

> 查于 2026-11-05。这一页只写**查证过的事实**和**取舍**，不写"应该可以"。
> 所有第三方协议端的行为都在变，动手前请再看一眼上游仓库。

---

## 一句话结论

| | 结论 |
|---|---|
| **QQ** | 你要的那一整套（聊天、表情包、语音、图片、私聊）**只有第三方协议端能做到**；官方 Bot 一半做不到。代价是**封号风险**，且这个风险落在你的号上，不落在代码上 |
| **B 站** | 弹幕有成熟的库（`blivedm`）；**发评论、回评论、私信没有官方 API**，全靠 cookie 模拟网页请求，风控比 QQ 更硬 |
| **表情包** | ⚠️ 这不是接入问题，是**"她能不能看图"**的问题。她能存表情包、也能发出去，但**看不懂表情包里是什么**——那要等「看」这一层 |

---

## 二、你要的每一项，能不能做

### QQ

| 你要的 | 能不能 | 靠什么 | 代价 |
|---|---|---|---|
| 基本聊天 | ✅ | NapCat / Lagrange 的 OneBot 事件 | 协议端要常驻 |
| 存表情包 | ✅ | 收 `image` 消息段 → 存到 `assets/stickers/` | 需要磁盘配额和去重 |
| **看**表情包 | ⚠️ **做不到（现在）** | 需要"她能看图"——多模态输入 | 见第三节 |
| 发表情包 | ✅ | 发 `image` 消息段（QQ 会把图当表情） | 无 |
| 发语音 | ✅ | 本地 TTS 出音频（已有）→ 转 silk/amr → `record` 段 | 要转码，QQ 只认特定格式 |
| 发图片 | ✅ | `image` 段 | 无 |
| 私聊 | ✅ | OneBot 私聊事件 | 无 |
| 群管理（禁言/踢人） | ✅ | OneBot API | 无 |

### B 站

| 你要的 | 能不能 | 靠什么 | 代价 |
|---|---|---|---|
| 看直播弹幕 | ✅ | [`blivedm`](https://github.com/xfgryujk/blivedm)（WebSocket，20+ 消息类型：弹幕/礼物/上舰/SC） | 无（不登录也能连，只是用户名打码） |
| 发弹幕 | ✅ | [`bilibili-api`](https://github.com/Nemo2011/bilibili-api) + SESSDATA | 有频率限制 |
| 看视频（她"看"视频内容） | ⚠️ | 能拿到标题/简介/封面/字幕，**看不懂画面** | 和表情包同一个问题 |
| 发评论 | ⚠️ | `bilibili-api` 的 comment 接口 + cookie | 风控严，新号容易触发验证 |
| **回复别人的评论** | ⚠️ | 同上 | 同上，且**最容易被判定为机器人** |
| 私信 | ⚠️ | `bilibili-api` 私信接口 + cookie | 需要 `buvid` + 签名；不是官方 API |

B 站没有给个人开发者开放"发评论/发私信"的官方接口。
所有这些库做的都是**模拟网页/APP 的请求**——技术上能用，但和 QQ 第三方协议端是同一类做法。

## 三、最重要的一条：表情包这题，卡在"看"

你说"存表情包、看表情包"，这是两件完全不同的事：

```
存  = 收到一个 image 消息段，把文件落盘      ← 纯工程，一天
看  = 知道这张图里是什么（猫？哭？嘲讽？）    ← 需要多模态输入
发  = 把文件当 image 段发出去                ← 纯工程，半天
```

**「看」这一层 2026-11-05 已经做了**（`tools/vision.mjs` + `/api/see`，见契约 2.23）。
所以现在她**能**看懂一张图——只是入口还只有"看一眼屏幕"。

所以 QQ 接上之后，她能做的是：

> 收到一张表情包 → 存下来 → 把图递给 `/api/see`（换个提示词）→ 记忆里有一条"他发了一张猫在哭的图"

要注意和屏幕那条的差别：**表情包是内容，不是隐私**，所以可以进记忆；
屏幕那条只进一句话、不念字，是因为那上面有别人的聊天记录。两条路用同一个模块，
但**提示词和"能不能留"是两件事**——不要因为复用了 `vision.mjs` 就复用它的隐私策略。

## 四、QQ 两条路：官方 Bot vs 第三方协议端

| | 官方 QQ 机器人开放平台 | 第三方协议端（NapCat / Lagrange / LLOneBot） |
|---|---|---|
| 登录 | 填 AppID + AppSecret，**不碰你的号** | **扫码登录你的真实 QQ 号** |
| 封号风险 | **无** | **有**。协议模拟违反 QQ 用户协议，腾讯明确禁止 |
| 功能 | 受官方开放范围限制 | 全功能（表情/语音/图片/私聊/群管理） |
| 稳定性 | 官方维护，变更提前公告 | 协议一变就挂，要等签名服务跟进 |
| 资源 | 纯 HTTP + WS，很低 | 要挂 QQ 客户端，内存几百 MB 起 |
| 现状 | 2026-03 起个人可创建 AI 机器人（单号最多 5 个）；但**主动消息推送** 2025-04 被移除，2026-06-22 群场景才恢复且要群主手动开 | NapCat（TypeScript，基于 NTQQ）最活跃；Lagrange（.NET，不装客户端）；go-cqhttp **已停止维护，不要用** |

**你要求"把 QQ 的功能都做了"，答案只有一个：走第三方。**
因为官方 Bot 做不到表情包和语音这一半。

**但代价要认清楚**：

- 用作机器人的 QQ 号会被判定为风险账号，可能警告、封禁、临时甚至永久冻结
- 用**小号**，不要用你的主号
- 网传封禁率高达 87%——这个数字来源不可靠，但"会封"是确定的
- 这不是代码能规避的，是协议本身的性质

## 五、架构：它们都是"外线"，不是新功能

按这套项目已经定下的规矩，QQ 和 B 站**都不该进大脑**。
它们和 `chat-in` 是同一层：外线适配器。

```
QQ 消息   ──┐
B站弹幕   ──┼──→ chat-in（合并、时机、上限）──→ 记忆 ──→ 她下一轮读到
语音输入  ──┘         ↑ source: 'qq' / 'bili' / 'voice'
```

她说话的时候，反过来：

```
她的动作/台词 ──→ 端口（avatar.speak / express）──→ 各平台适配器发出去
                                                    ↑ 表情包、语音、图片也走端口
```

**三条不许破的线**（和 2.20 语音那一节一致）：

1. **平台消息进来时只带文本和出处**。不要把 QQ 的原始 JSON 塞进记忆——
   那是"把外线协议带进她的世界"，以后换协议要改记忆。
2. **"他说完了"由平台的事件给**，不许自己攒批猜（群里刷屏时才需要攒批，那是 chat-in 的事）。
3. **发出去的东西不许绕过端口**。她想发表情包，是"她选择发一张图"，
   不是"程序在某个回调里调了 QQ API"。

## 六、三个真坑（提前说，省你两天）

**① 私聊回复评论会被判成营销号。**
B 站对"新号 + 高频回复 + 带链接"的组合极其敏感。第一天就自动回评论，大概率喜提验证码。
建议：先只**看**（弹幕、评论），要回的时候让人点一下确认。

**② QQ 语音不是发 mp3。**
QQ 的语音消息要 AMR/silk 之类，得转码。已经有 TTS 出音频，但"能出声"和"QQ 能播"是两件事。

**③ 多平台同时说话会串。**
她在 QQ 群里说了一句，B 站直播间也会说一句吗？这是**产品决定**，不是技术决定。
建议先做"一个平台一个实例"，别急着打通。

## 六点五、B 站登录：扫码能拿到什么，拿不到什么

你说"B 站也要可以登录的才行"。这一条成立，因为**不登录只能看，不能发**：

| | 不登录 | 登录 |
|---|---|---|
| 看直播弹幕 | ✅ 能连，但**用户名打码、UID 变 0** | ✅ 完整 |
| 发弹幕 | ❌ | ✅ |
| 发评论 / 回评论 | ❌ | ✅（有频率限制） |
| 私信 | ❌ | ✅ |

### 三条登录路

| 方式 | 怎么做 | 评价 |
|---|---|---|
| **扫码**（推荐） | `login_v2.QrCodeLogin(platform=WEB)` → 出二维码 → 手机 B 站扫 → 轮询 `check_state()` | 不碰密码，不触发极验，一次能拿一整套 cookie |
| **手填 SESSDATA** | 浏览器 F12 → Application → Cookies → 复制 `SESSDATA` | 最快，但只填一个字段经常不够（还要 `bili_jct` 做 CSRF、`buvid3` 过风控） |
| 账号密码 | RSA 加密 + **极验滑块** | 别做。极验要打码平台，等于把账号密码交给第三方 |

### 扫码之后拿到的是四个字段，不是一个

```
SESSDATA      登录态本体（有效期以周计）
bili_jct      CSRF token，所有写操作（发评论/发弹幕）必须带
buvid3        设备指纹，缺了容易被判定为异常请求
DedeUserID    你自己的 UID
```

**只存 SESSDATA 是不够的**——很多人第一次接 B 站都栽在这儿：能读不能写，报的错还含糊。

### 存哪儿

```
secrets/bili.json     ← 不进仓库（和 keys.json 同级待遇）
```

`bilibili-api` 里是 `Credential(sessdata=, bili_jct=, buvid3=, dedeuserid=)`。
换成本地 whisper 那种"换一个参数"的设计：凭证从文件读，不写进代码。

### ⚠️ 登录 ≠ 不被风控

这是最容易误解的一条：

- **登录**解决的是"你是谁"
- **风控**判断的是"你的行为像不像人"

登录之后照样会被拦。典型表现：HTTP 412、要求滑块验证、评论发出去只有自己可见、私信进垃圾箱。
新号 + 高频 + 带链接 = 最容易被判定的组合。

所以"能登录"只是拿到了入场券，**不代表可以自动回复评论**。
我的建议仍然是：B 站先只做「看」（弹幕、评论），要「发」的时候让人点一下确认。

## 七、建议的顺序

```
第零步（半天）
  把两边的登录做掉、凭证存进 secrets/（不进仓库）：
    QQ  → NapCat 扫码登录（登录的是你的 QQ 号，用**小号**）
    B站 → 扫码（QrCodeLogin）拿 SESSDATA + bili_jct + buvid3 + DedeUserID
  这一步不做完，后面所有「发」类操作都是空的

第一步（便宜、当天能用）
  接 QQ（NapCat + OneBot WS）→ 只做文字收发 → 走 chat-in
  这一步不需要改大脑，只是多一个适配器

第二步（便宜）
  表情包：存 + 发（不解释内容）
  发语音：TTS → 转码 → record 段

第三步（中等）
  B 站直播弹幕（blivedm）→ 走 chat-in
  只读不发，先让她"听见直播间"

第四步（贵，且有风险）
  发评论 / 回评论 / 私信
  建议做成"她说要发，你点确认"——不给全自动

第五步（底层已就绪，还差入口）
  「看」表情包 / 看视频 / 看屏幕
  ✅ 视觉那一层 2026-11-05 做了：一帧图 → 一句话（tools/vision.mjs + /api/see）
     还差的只是"从哪拿到图"和"看完留什么"——屏幕那条只留一句话，表情包可以留描述
```

## 七点五、不用装 NapCat 也能先验这一步

`tools/qq-replay.mjs`：把一份导出的聊天 JSONL（每行 `{conv,kind,ts,qq,nick,text}`）
按原顺序、压缩后的间隔，一句一句 POST 到 `/api/in`，就像协议端正往外吐消息。
它**不是适配器**——不连协议、不重连、不鉴权，只回答一个问题：她接不接得住群聊。

```bash
node tools/qq-replay.mjs --file <导出的.jsonl> --conv <群号> --offset 40000 --n 8 --gap 400
# --dry 先看发什么；--watch 40 盯她多久的回复（默认读 logs/chat-*.jsonl 的新增行）
```

实测（2026-11-05，真群聊记录、真模型）：

| 发法 | 她做了什么 |
|---|---|
| 8 句压到 400ms 一条（约 3.2 秒灌完） | 合成 **1 批 → 1 轮**，回"你们俩聊吃的…"，认得出两个说话人 |
| 3 句、每句隔 2.6 秒 | **3 批 → 3 轮**，5 秒里说了三句 |

所以 `window` 管的是"她**什么时候看**"，不是"她**多久说一次**"。
一个人私聊够用；真进群，还得再定一条**说完之后的冷却**——谁在说、说了几条，
那些属于"她要不要接"的判断，不要写成按内容过滤的规则（那又变成外部算法替她想）。
